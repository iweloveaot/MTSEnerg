# МТС Energytool — консультант и заявки

Python-приложение: поиск по базе знаний → консультация → явное согласие → сбор контактов → сохранённая заявка. Есть веб-чат, просмотр истории и отдельный пакетный режим для платформы. Поиск `lexical-focus-v5`, промпт `consult-v5`; база знаний подключается извне.

## Быстрая проверка

Нужны Python 3.12 либо Docker с Compose, доступ к API модели и предоставленный организаторами `knowledge-base.zip`. Поместите архив в корень проекта. Создайте `.env` на основе `.env.example`, заполните `LLM_BASE_URL` (с `/v1`), `LLM_MODEL`, `LLM_API_KEY`. Действующие ключи в комплект сдачи не включены.

```powershell
docker compose up --build -d
```

Открыть http://127.0.0.1:8000/. `/api/health` проверяет процесс, `/api/ready` выполняет запрос модели. Перед запуском остановите локальный сервер на порту 8000. Данные сохраняются в томе `energytool_data`, база знаний подключается только для чтения. `docker compose restart energytool` перезапускает сервис; `docker compose down` и `docker compose up -d` пересоздают контейнер с сохранением тома. Параметр `down -v` удаляет данные и для проверки сохранности не используется.

Без Docker:

```powershell
python -m pip install -r requirements.txt
python solution.py --serve
```

## Проверка сценария

1. Спросить про учёт электроэнергии на складе, уточнить детали; открыть отладку и проверить источники.
2. Написать «Оформить заявку» и передать вымышленные контакты: «Меня зовут Анна Иванова. Компания Ромашка. Телефон 89991234567».
3. Проверить карточку заявки, исправить телефон и открыть сохранённый разговор через историю.
4. Начать новый диалог: он не должен содержать контекст первого. Проверить отказ от контактов и продолжение консультации.
5. После перезапуска и пересоздания контейнера проверить сохранность истории и заявки.

## Платформа и архивы

`submission.zip` — плоский архив для автоматической проверки. Его точка входа `python solution.py`: читает `$DATA_DIR/questions.csv` и архив знаний, создаёт `submission.csv` с колонками `id,answer`, сохраняя ID и порядок. Каждая строка обрабатывается независимо. Настройки модели передаются через окружение. В плоском архиве нет веб-приложения и данных организаторов.

```powershell
python build_submission.py
python solution.py --data-dir data --output submission.csv
```

Полный исходный архив предназначен для запуска продукта и Docker-проверки. Новую воспроизводимую копию комплекта создаёт `python build_final_release.py`. Он сохраняет предыдущие сборки и пишет контрольные суммы. База знаний, вопросы, история, ключи и резервные копии в исходный архив не включаются.

## Архитектура и ограничения

А: `backend/`, `orchestration.py`, `solution.py`, сборка. Б: `consultation_agent/` и генерируемый `energytool_rag.py`. В: `application_agent/`, `frontend/`. Состояние сессий и заявок хранится в SQLite; заявка в одной сессии обновляется без создания дубликата. Оркестратор работает и в чате, и в пакетной проверке.

Модули проверяют формат ответа, ссылки на разделы и числовые суммы в рублях, но не гарантируют достоверность каждого свободного ответа модели. Извлечение контактов и резюме основаны на правилах; сложные формулировки требуют ручной проверки. Реальной отправки в CRM или почту нет. Архив читается в интерфейсе только для просмотра. Кнопка нового диалога меняет UUID, но не помечает предыдущую сессию закрытой на сервере; API закрытия предусмотрен отдельно.

Сервер запускается одним процессом. `metrics` в ответе API содержит время поиска, генерации, полной обработки и число логических вызовов модели. Сетевые повторы входят во время генерации. Веб-клиент повторяет временные сбои до двух раз; таймаут задаётся на попытку. Содержимое диалога не пишется в служебные метрики. Внешнее размещение требует ограничения доступа к истории; Compose привязывает порт к localhost.

Подробности API и пакетного режима — в `BACKEND.md`; результаты и оставшиеся проверки — в `RELEASE_CHECKLIST.md`; отчёты Б — в `docs/DAY4_B.md` и `docs/DAY5_B.md`.
