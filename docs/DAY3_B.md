# МТС EnergyTool · участник Б · день 3

Консультант учитывает текущую задачу клиента, продолжает отвечать после отказа от контактов и предлагает перейти к заявке, когда для расчёта или проверки объекта нужен специалист. Поиск `lexical-focus-v3`, промпт `consult-v3`.

## Многошаговая консультация

- При явной смене темы поиск использует реплики по новой задаче. При явном возврате по названию темы он подбирает до трёх связанных реплик клиента из доступной истории.
- Промпт просит сохранять уже известные параметры объекта, учитывать явно исправленное значение и задавать один вопрос при существенном противоречии. Факты о клиенте берутся из его реплик. Факты о продукте берутся из найденных разделов базы.
- При переходе к расчёту консультант может добавить приглашение написать «Хочу оформить заявку». Это команда согласия, которую уже распознаёт обработчик А. Приглашение само по себе сохраняет заявку в состоянии черновика. Сбор контактов начинается после явного согласия. При отказе, который зафиксировал агент заявки, приглашение подавляется даже при соответствующем сигнале модели.

Проверил девять диалогов с ручной имитацией Qwen. В них были известные и недостающие вводные, исправление числа приборов, противоречие, смена темы и возврат, предложение менеджера, отказ и технический вопрос вне базы. Для запроса точного расчёта добавил поиск вводных по продукту, который клиент назвал в предыдущей реплике. Все 25 случаев дня 2 с использованными источниками сохранили эти источники в первых пяти результатах.

## Подключение к ветке А

Подготовлен и проверен локальный патч `qa-local/day3_backend.patch` для снимка `origin/dev-a` на коммите `d85fa36`. После появления `energytool_rag.py` в общей сборке А может проверить патч через `git apply --check <путь-к-патчу>` и применить его через `git apply <путь-к-патчу>`. Переменная `ENERGYTOOL_KB_PATH` должна указывать на локальный `knowledge-base.zip`.

Патч загружает индекс при запуске чата, подключает консультанта к общему обработчику и сохраняет строковый формат `sources`, который понимает интерфейс. Адаптер передаёт модели системную инструкцию консультанта. Обработчик передаёт в консультант признак отказа от контактов из агента В. Агент В получает исходную историю этой сессии в своём существующем формате.

На Python 3.12 через общий обработчик А, реальный агент В и SQLite прошли сценарии явного согласия, сбора контактов, продолжения консультации после отказа, повторного открытия базы и изоляции сессий. Вызов API модели подменён, HTTP и браузерный интерфейс отдельно не прогонялись. В инструкции А указан Python 3.9. В `application_agent/agent.py` и `application_agent/extractor.py` используются вычисляемые при импорте аннотации `str | None`, которым требуется Python 3.10 или новее.

## Проверка резюме агента В

Проверил резюме на снимке `origin/dev-v` (`3e5fd33`). Код агента совпадает со снимком в ветке А. Встроенные 28 тестов В прошли. Отдельные диалоги выявили следующие расхождения.

| Диалог | Что вышло | Что должно попасть в резюме |
| --- | --- | --- |
| Клиент поздно исправил количество с 40 на 24 | Сохранилось 40. Исправление не попало в обстоятельства | Использовать актуальные 24 счётчика |
| Клиент перешёл с солнечных панелей на учёт в цехах | Главной задачей остались панели | Указать, что сейчас клиент обсуждает учёт в цехах |
| На вопрос о моделях клиент ответил «пока не знаю» | Список открытых вопросов пуст | Оставить модели приборов как недостающее сведение |
| Консультант дал рекомендацию и задал вопрос одной репликой | Вся реплика оказалась в открытых вопросах | Сохранить рекомендацию в обсуждении, а вопрос отдельно |

Стенограмма и фактическое резюме по каждому из этих сценариев находятся в `qa-local/day3_summary_review.json`. Результаты консультации с найденными источниками находятся в `qa-local/day3_dialogues.jsonl`.
