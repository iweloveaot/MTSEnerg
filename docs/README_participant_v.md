# Участник В — агент заявки и интерфейс чата

**Проект:** МТС Energytool — ИИ-консультант для сайта  
**Ветка разработки:** `dev-v`  
**Статус на 11 ноября 2026:** локальная реализация модулей и интерфейса; интеграция с backend и RAG ещё не проверена.  
**Для кого документ:** участники А (backend/оркестрация/сессии), Б (RAG/качество консультации), остальные участники команды.

> Это README части участника В. Основной `README.md` в корне репозитория остаётся общекомандным. Файл `docs/chat_api_contract.md` — **предложение API к согласованию**, а не подтверждённый интерфейс сервера.

## 1. Что уже реализовано

### Агент заявки (`application_agent/`)

| Файл | Ответственность |
| --- | --- |
| `models.py` | Dataclass-модели `Message`, `Contacts`, `ApplicationSummary`, `ApplicationAgentInput`, `ApplicationAgentResult`; входной флаг `application_requested` (по умолчанию `False`). |
| `validator.py` | Нормализация российских телефонных номеров к `+7XXXXXXXXXX`, отбрасывание нераспознанных номеров. |
| `extractor.py` | Извлечение явно сформулированных ФИО, телефона и компании из **сообщений пользователя**; новые явно указанные значения заменяют старые; распознавание некоторых формулировок отказа от контактов. |
| `summarizer.py` | Предварительное *извлекающее* резюме из истории диалога: проблема, обстоятельства, обсуждение, незакрытый вопрос; базовая очистка контактных фрагментов. |
| `agent.py` | `run_application_agent(...)`: объединение извлечения, валидации и резюме; вычисление `missing_fields`, `next_question`, `ready`, `status`. |
| `serializer.py` | `result_to_dict(...)` и `result_to_json(...)` для передачи результата через API. |
| `__init__.py` | Экспорт публичных Python-моделей и `run_application_agent`. |

**Правила заявки:**

- `application_requested=False`: не задавать следующий вопрос о контактах; не считать заявку готовой, даже если все контакты известны.
- `application_requested=True`: разрешён сбор недостающих полей, если клиент не отказался.
- `contact_collection_declined=True` или распознанный отказ: прекратить сбор контактов; консультацию при этом должен продолжать основной консультант.
- `ready=True` только при явном запросе заявки, отсутствии отказа и наличии всех трёх валидных контактных полей.
- `status` — `draft`, `ready` или `declined`. Согласие и отказ влияют на готовность, но черновик может содержать частично заполненные контакты.
- Сам модуль **не отправляет** данные в CRM/почту и **не сохраняет** историю в БД.

### Веб-интерфейс (`frontend/`)

| Файл | Ответственность |
| --- | --- |
| `index.html` | Разметка чата, кнопки «Новый диалог», карточки заявки и debug-панели. |
| `styles.css` | Адаптивный интерфейс с красными акцентами в стилистике МТС. |
| `app.js` | Отображение сообщений, `POST /api/chat`, обработка ошибок, сброс интерфейса и идентификатора сессии, отображение заявки, времени ответа и источников. |

**Проверено вручную в браузере:** отображается пользовательское сообщение; при отсутствии backend выводится понятное сообщение об ошибке; кнопка «Новый диалог» очищает текущий чат; debug-панель открывается. Реальные ответы модели, источники RAG и карточка готовой заявки **пока не проверены через backend**.

Безопасность UI: сообщения выводятся через `textContent`, а не `innerHTML`, чтобы не выполнять HTML/JS из текста клиента и модели.

## 3. Как запустить интерфейс локально

Запуск только **статических файлов** (не запускает AI/backend):

```bash
cd ~/MTSEnerg/frontend
python3 -m http.server 8000
```

Открыть `http://localhost:8000/`. Стили и JavaScript загрузятся, однако отправка сообщения на `/api/chat` будет возвращать ошибку, пока на том же адресе/порту не будет доступен backend. Команда `python3 -m http.server` не обрабатывает POST-запросы — это ожидаемо.

Для полноценного сценария участнику А требуется раздача frontend из backend или настройка согласованного адреса API. Приоритет — **один origin** для UI и `/api/chat`, без ненужного CORS.

## 4. Текущий Python-интерфейс для участника А

Импорт:

```python
from application_agent import (
    ApplicationAgentInput,
    Contacts,
    Message,
    run_application_agent,
)
from application_agent.serializer import result_to_dict
```

Пример с **тестовыми** контактами:

```python
request = ApplicationAgentInput(
    session_id="demo-session-1",
    messages=[
        Message(role="user", content="У нас выросли счета за электричество."),
        Message(role="user", content="Меня зовут Анна Иванова."),
        Message(role="user", content="Компания Ромашка."),
        Message(role="user", content="Мой телефон 8 (999) 123-45-67."),
    ],
    current_draft=Contacts(),
    application_requested=True,
)

result = run_application_agent(request)
payload = result_to_dict(result)
```

Возвращаемые поля `payload`:

```json
{
  "contacts": {
    "full_name": "Анна Иванова",
    "phone": "+79991234567",
    "company": "Ромашка"
  },
  "missing_fields": [],
  "next_question": null,
  "summary": {
    "problem": "У нас выросли счета за электричество.",
    "circumstances": "",
    "discussed_solution": "",
    "open_questions": []
  },
  "ready": true,
  "contact_collection_declined": false,
  "status": "ready"
}
```

Здесь структура — иллюстрация; точное содержание резюме определяется переданной историей и текущей реализацией `summarizer.py`. `session_id` передаётся во входе, но **не входит** в `ApplicationAgentResult`, поэтому backend должен хранить его отдельно.

**Важный принцип интеграции:** агент заявки не должен сам определять, когда продавать продукт или навязывать контакты. Основной консультант управляет диалогом и явным переходом к заявке; `application_requested` передаётся в агент осознанно. Решение о том, как получать согласие через UI/диалог, ещё не принято.

## 5. Предложенный HTTP-контракт: требует согласования с А

Frontend **сейчас ожидает** следующий запрос:

```http
POST /api/chat
Content-Type: application/json
```

```json
{
  "session_id": "uuid-текущего-диалога",
  "message": "Текст клиента"
}
```

Ожидаемый JSON-ответ:

```json
{
  "answer": "Ответ консультанта, основанный на базе знаний",
  "sources": ["название реально использованного документа"],
  "application": null
}
```

`application` может быть `null` либо объектом с полями из `result_to_dict(...)`; карточка заявки в текущем UI показывается только при `application.ready === true`. `sources` пока ожидается как массив **строк**; если backend возвращает объекты-источники, нужно согласовать адаптацию.

**Пока не согласованы:** путь endpoint, формат ошибок, метаданные источников, хранение истории, восстановление старой сессии, передача согласия, возможное явное действие «Оформить заявку», раздача статических файлов, схема сброса сессии на сервере.

### Участнику А — что требуется и что можно использовать

1. Подтвердить/предложить окончательный HTTP-контракт, включая `session_id`, `answer`, `sources`, `application` и ошибки.
2. Определить, как frontend включает **явное согласие** (`application_requested`); текущий `/api/chat` посылает только `session_id` и `message`, поэтому согласие по API пока не передаётся.
3. Подключить `run_application_agent(...)` в цепочку обработки сообщений; передавать историю **только текущего диалога** и черновик контактов текущей сессии.
4. Реализовать устойчивое хранение истории **всех** сессий (включая без заявки), а также корректный сброс контекста при новом диалоге. Смена UUID в UI сама по себе не сохраняет и не удаляет серверную историю.
5. Раздавать `frontend/` из общего приложения или сообщить фактический адрес API и способ запуска через Docker.
6. Подключить реальную карточку заявки, проверить end-to-end сценарий, в том числе ошибки и отказ от телефона.
7. Согласовать экспорт/использование `result_to_dict(...)` и кому принадлежит окончательная схема HTTP-ответа.

### Участнику Б — вопросы и точки подключения

1. В каком виде RAG возвращает ответ: текст, ссылки на документы, их названия/идентификаторы, возможные цитаты?
2. Нужен список **фактически использованных** документов для debug-панели; не подставлять вымышленные источники.
3. Где проходит граница ответственности: B отвечает за корректность консультации по базе знаний, V — за контакты/резюме/отображение, A — за orchestration/API/сессии.
4. По возможности передавать в агент заявки подтверждённое описание обсуждённого решения — текущий `summarizer.py` извлекает его из сообщений ассистента, не перепроверяя по базе знаний.

## 6. Известные ограничения и риски

- `extractor.py` использует регулярные выражения и **не гарантирует** распознавание произвольных формулировок ФИО, компании, исправлений и отказов.
- `summarizer.py` является предварительным извлекающим резюме; не всегда отличает существенное от второстепенного. Простое правило «пользователь ответил после вопроса» может ошибочно считать вопрос закрытым.
- Очистка ФИО/телефонов в резюме — **частичная**, не гарантия полного удаления персональных данных. Не использовать реальные персональные данные в тестах/демо.
- `normalize_phone` рассчитан на российские номера и не является универсальной телефонной библиотекой.
- История и черновик **не хранятся** агентом автоматически: это ответственность backend.
- Кнопка «Новый диалог» в текущем JS сбрасывает UI/UUID, но не реализует серверную команду архивирования/сброса.
- Веб-интерфейс ещё не проходил end-to-end тест с реальным backend и RAG. Пока отсутствуют интеграционные тесты HTTP, доступности и восстановления после ошибок.
- Перед отправкой в Git проверить состав изменений, чтобы не добавить данные кейса из ZIP, секреты, `.env`, виртуальные окружения и лишние артефакты.

## 7. Приоритеты дальнейшей работы

1. Согласовать HTTP-контракт с участником А и источники с участником Б.
2. Подключить реальный backend и проверить «консультация → явное согласие → контакты → заявка».
3. Проверить отказ от контактов, исправления, переход между темами, новый диалог и сохранение всех сессий.
4. Проверить в debug-панели настоящее время ответа и документы, использованные RAG.
5. Доработать качество извлечения/резюме по воспроизводимым тестовым случаям и проверить запуск в общем Docker-стеке.

## 8. Ограничения кейса, о которых важно помнить всей команде

- Факты об Energytool, продуктах, тарифах, стоимости и условиях — **только из предоставленной базы знаний**.
- Если ответ в базе не найден — честно сообщить об этом и предложить специалиста; не выдумывать.
- Реальная интеграция с CRM/почтой для прототипа не обязательна.
- Не публиковать исходные выгрузки организаторов в открытом репозитории; не коммитить реальные API-ключи и персональные данные.
- Контекст нового диалога должен быть чистым, но история всех сессий должна сохраняться для проверки.
