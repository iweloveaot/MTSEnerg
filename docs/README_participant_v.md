## 2. Агент заявки (`application_agent/`)

| Файл | Назначение |
| --- | --- |
| `models.py` | Модели сообщений, контактов, резюме, входа и результата агента |
| `validator.py` | Нормализация и проверка номера телефона РФ |
| `extractor.py` | Извлечение имени, компании и телефона из сообщений пользователя; исправления и отказ |
| `summarizer.py` | Извлекающее резюме проблемы, обстоятельств, обсуждения и открытых вопросов |
| `agent.py` | `run_application_agent(...)`, готовность заявки и следующий вопрос |
| `serializer.py` | Преобразование результата в словарь/JSON |
| `__init__.py` | Публичные импорты агента |

**Правила:**

- Без явного согласия на заявку (`application_requested=False`) агент не должен запрашивать контакты только ради заявки, даже если некоторые данные уже известны.
- После согласия агент запрашивает только недостающие контактные поля. Для `ready=True` нужны явное согласие, отсутствие отказа, ФИО, телефон и компания.
- При отказе от передачи контактов сбор прекращается, а основная консультация может продолжаться.
- Явные исправления имени, телефона, компании и количества счётчиков должны заменять устаревшие данные; явная смена основной темы должна учитываться в резюме.
- Неизвестные детали, например мощность объекта, нельзя придумывать.
- Возможные значения статуса заявки: `draft`, `ready`, `declined`.

Агент сам **не сохраняет** сессии в SQLite и **не отправляет** заявки в CRM или по электронной почте. Это ответственность backend и дальнейшей интеграции.

### Python-интерфейс

```python
from application_agent import ApplicationAgentInput, Contacts, Message, run_application_agent
from application_agent.serializer import result_to_dict

request = ApplicationAgentInput(
    session_id="demo-session-1",
    messages=[
        Message(role="user", content="У нас выросли счета за электричество."),
        Message(role="user", content="Меня зовут Анна Иванова."),
        Message(role="user", content="Компания Ромашка."),
        Message(role="user", content="Телефон 8 (999) 123-45-67."),
    ],
    current_draft=Contacts(),
    application_requested=True,
)

result = run_application_agent(request)
payload = result_to_dict(result)
```

Пример использует вымышленные данные. Возвращаемый объект включает `contacts`, `missing_fields`, `next_question`, `summary`, `ready`, `contact_collection_declined`, `status`. Конкретный текст резюме определяется историей диалога. `session_id` учитывается backend отдельно от результата агента.

## 3. Веб-интерфейс (`frontend/`)

| Файл | Назначение |
| --- | --- |
| `index.html` | Чат, кнопки заявки, история, карточка заявки, отладочная панель |
| `styles.css` | Адаптивное оформление в стилистике МТС |
| `app.js` | Запросы к API, сообщения, заявка, история, состояния и ошибки |

Интерфейс предоставляет:

- Отправку сообщений через `POST /api/chat` с `session_id` и `message`.
- Отображение ответа, названий источников (если они получены от backend), времени ответа и карточки заявки.
- Кнопки «Оформить заявку» и «Продолжить консультацию» **только** при `offer_application: true`.
- Загрузку списка диалогов через `GET /api/sessions` и открытие истории через `GET /api/sessions/{session_id}`.
- Просмотр ранее сохранённой переписки только для чтения и возврат к текущей беседе без потери её отображаемых сообщений.
- Кнопку «Новый диалог» с новым идентификатором сессии; это сбрасывает контекст нового общения, но само по себе не закрывает прежнюю сессию на сервере.
- Сообщения об ошибках API; при ошибке предложения заявки кнопки восстанавливаются.

**Безопасный вывод:** текст сообщений и источников добавляется через `textContent`, а не исполняется как HTML/JavaScript.

**Ограничение безопасности:** доступные сейчас `GET /api/sessions` и `GET /api/sessions/{session_id}` не обеспечивают изоляцию пользователей посредством авторизации. Публичное развёртывание истории требует разграничения доступа на backend. Список всех сессий допустим только для контролируемого локального прототипа.

## 4. Подтверждённые HTTP-маршруты

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/chat` | Сообщение консультанту |
| `POST /api/sessions` | Создание сессии |
| `GET /api/sessions` | Список сохранённых сессий |
| `GET /api/sessions/{session_id}` | История, статус и заявка сессии |
| `POST /api/sessions/{session_id}/close` | Закрытие сессии |
| `GET /api/health` | Проверка запуска backend |
| `GET /api/ready` | Проверка доступа к внешней модели |

Это фактические маршруты текущего `backend/app.py`, а не предложения на будущее. Старый файл `docs/chat_api_contract.md` может содержать предварительные договорённости; при расхождениях ориентироваться на код backend и согласовывать изменения с А.

## 5. Запуск локального веб-чата

Из корня проекта в WSL Ubuntu, в активном окружении проекта:

```bash
cd ~/MTSEnerg
.venv/bin/python -m uvicorn backend.app:create_app --factory --host 127.0.0.1 --port 8000
```

Открыть в браузере: `http://127.0.0.1:8000/`. Серверный терминал оставить запущенным. Проверки из другого терминала:

```bash
curl -i http://127.0.0.1:8000/api/health
curl -i --max-time 100 http://127.0.0.1:8000/api/ready
```

Для RAG локально требуется доступ к `knowledge-base.zip` от организаторов (в корне проекта или по пути, заданному `KNOWLEDGE_BASE_PATH`). Для внешней LLM используются `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` и необязательный `LLM_TIMEOUT_SECONDS` (локально через `.env`, который не публикуется). Не выводить и не коммитить секреты. Успешный `/api/health` **не означает** доступность LLM; её отдельно проверяет `/api/ready`.

Режим `python3 -m http.server` раздаёт лишь статические файлы и **не** обслуживает `/api/chat`; для полноценной проверки использовать backend.

## 8. Известные ограничения и передача коллегам

- `extractor.py` использует эвристики и регулярные выражения; произвольные формулировки ФИО, компании и отказа могут требовать дополнительных тестов.
- `summarizer.py` формирует извлекающее резюме, а не гарантированно полное и идеальное смысловое описание. Очистка персональных данных частичная.
- Нормализация телефона ориентирована на российские номера.
- Интеграция с CRM/почтой отсутствует и не требуется для текущего прототипа.
- История и заявки хранятся backend в SQLite; агент и frontend не заменяют серверную авторизацию.
- Отсутствие авторизации на маршрутах истории нужно устранить до публичного размещения.
- Ошибки внешнего LLM (`model_auth_error`, тайм-ауты) передавать А; на платформе организаторы предоставляют служебные переменные окружения автоматически.
- Проверку поиска по реальному корпусу и локальные QA-материалы `qa-local` ведёт Б.
- В Git не включать `.env`, API-ключи, `knowledge-base.zip`, данные организаторов, реальные контакты клиентов и локальные служебные файлы.
- Для финальной сдачи по техническому регламенту требуется корневой ZIP с `solution.py`, нужными `.py`-модулями и `requirements.txt`; `frontend/` не является обязательной частью автоматического сабмита. Сборкой занимается А.
