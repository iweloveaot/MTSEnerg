
# Chat API Contract

Статус: предложение для согласования с участником А.

## Endpoint

POST /api/chat

## Запрос

```json
{
  "session_id": "unique-session-id",
  "message": "У нас выросли счета за электроэнергию"
}
```

### Поля запроса

- session_id: идентификатор текущего диалога.
- message: текст нового сообщения пользователя.

## Успешный ответ

```json
{
  "answer": "Текст ответа консультанта",
  "sources": [
    "Название документа базы знаний"
  ],
  "application": {
    "contacts": {
      "full_name": null,
      "phone": null,
      "company": null
    },
    "missing_fields": [
      "full_name",
      "phone",
      "company"
    ],
    "next_question": null,
    "summary": {
      "problem": "Описание задачи клиента",
      "circumstances": "",
      "discussed_solution": "",
      "open_questions": []
    },
    "ready": false,
    "contact_collection_declined": false,
    "status": "draft"
  }
}
```

`application` может быть `null`, если данные заявки
пока не формировались.

## Правила

1. Ответ консультанта формирует backend с использованием
   базы знаний Energytool.
2. Агент заявки обрабатывает контакты и резюме.
3. Контакты не запрашиваются без согласия клиента.
4. При отказе от контактов консультация продолжается.
5. session_id сохраняется в течение одного диалога.
6. Новый диалог получает новый session_id.
7. История диалогов сохраняется на backend.
8. sources содержит документы, реально использованные
   при формировании ответа.
9. Время ответа измеряется в интерфейсе.
10. Ошибки API не должны приводить к потере интерфейса.

- Как интерфейс должен передавать согласие на заявку?
- Где будет размещаться frontend при запуске через Docker?
